## ① 表 3 最后一列「关闭缓存平均响应 / ms」——最要紧

**现状**

| 并发用户数 | 平均响应 / ms | 关闭缓存平均响应 / ms | 对比 |
|---|---|---|---|
| 50 | 86 | 96.8 | 关缓存慢 13% |
| 100 | 128 | 95.6 | 关缓存**快 25%** |
| 200 | 216 | 94.2 | 关缓存**快 56%** |
| 500 | 452 | 92.5 | 关缓存**快 80%** |

**问题**：关掉缓存反而更快，而且并发越高越快。这在物理上讲不通，审稿人看到会连带怀疑整个测试。

**我的判断**：这四个数（96.8 / 95.6 / 94.2 / 92.5）随负载单调下降，特征完全符合**缓存命中率（%）**，多半是填错了列。

**两条出路，选一条：**

**A. 如果这四个数确实是缓存命中率** —— 把列名改成 `缓存命中率 / %`，并把 4.6 节那句关于缓存的话改成：

> 系统引入 Redis 缓存应对高频积分查询，采用 Cache-Aside 模式（写入时先更新数据库再删除缓存），并以空值缓存与分布式锁分别防止缓存穿透与击穿[15]。实测缓存命中率在 50～500 并发下保持在 92.5% 以上（表 3）。

**B. 如果要保留「关闭缓存响应时间」这一列** —— 需要补一次关缓存的压测。正确的数应当**明显高于开缓存**且**随并发增长**，例如 50 并发 300+ ms、500 并发 2000+ ms 这个量级。跑一次 JMeter 半小时就能拿到。

> B 更有价值：它能把"我们用了 Redis"变成"缓存带来 × 倍提升"，是审稿人喜欢看到的证据。

## ④ 测试环境：4 核 CPU / 500 GB 内存

格式我已经规范成 `4 核 CPU / 500 GB 内存、Ubuntu 24.04 LTS、OpenJDK 21、MySQL 8.0 与 Redis 7.2`，
但**数值本身请你确认**：4 核配 500 GB 内存不合常理（500 GB 是数据中心级配置，
而 4 核是入门级）。常见的情况是——

- 500 GB 其实是**硬盘**容量 → 写成 `4 核 CPU / 16 GB 内存 / 500 GB 硬盘`
- 内存实际是 16 GB 或 32 GB → 直接改数字

审稿人对这类配置很敏感，不改容易被追问。
