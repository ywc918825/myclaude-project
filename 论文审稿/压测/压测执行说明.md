# 表 3 重跑：半小时拿到真实数据

四档压测各 5 min，加上准备时间，**净耗时约 30 分钟**，其中大部分是等待。

---

## 0. 准备（约 5 min）

**装 JMeter**（如果还没有）：

```bash
# 需要 JDK 8+
wget https://dlcdn.apache.org//jmeter/binaries/apache-jmeter-5.6.3.tgz
tar xzf apache-jmeter-5.6.3.tgz
export PATH=$PWD/apache-jmeter-5.6.3/bin:$PATH
```

**准备 `users.csv`**（放在 `压测计划.jmx` 同目录），从库里导 200 条真实用户即可：

```csv
userId,deptId
1001,3
1002,3
1003,7
...
```

```sql
-- 大致这样导
SELECT id, dept_id FROM sys_user WHERE status = 1 LIMIT 200;
```

**拿一个 JWT**（登录一次，从响应里抄 token）。

**核对 `压测计划.jmx` 里的三个接口路径**——我按论文里"积分查询 / 画像生成 / 排行统计"
写的是占位路径，改成你系统里真实的：

```
/api/points/query        积分查询
/api/profile/radar       画像生成
/api/rank/list           排行统计
```

## 1. 跑四档（约 20 min，纯等待）

```bash
mkdir -p out
for U in 50 100 200 500; do
  jmeter -n -t 压测计划.jmx \
         -Jhost=<服务器IP> -Jport=8080 -Jtoken=<你的JWT> \
         -Jusers=$U -Jrampup=30 -Jduration=300 \
         -l out/$U.jtl
  echo "=== $U 并发跑完，歇 60 s 让系统回稳 ==="
  sleep 60
done
```

- `-Jrampup=30`：30 s 内把线程拉满，避免一上来就打爆
- `-Jduration=300`：每档跑 5 min
- 两档之间 `sleep 60`，让连接池和 GC 回到基线

> **注意**：压测机和被测服务**不要放同一台机器**，否则 JMeter 自己会抢 CPU，
> 测出来的响应时间偏高、吞吐偏低。

## 2. 取缓存命中率

命中率不在 JMeter 里，要从 Redis 拿。**每档开始前清零、结束后读数**：

```bash
# 每档开始前
redis-cli CONFIG RESETSTAT

# 每档结束后
redis-cli INFO stats | grep keyspace
# keyspace_hits:184320
# keyspace_misses:6144
# 命中率 = 184320 / (184320 + 6144) = 96.77%
```

一行搞定：

```bash
redis-cli INFO stats | awk -F: '/keyspace_hits/{h=$2} /keyspace_misses/{m=$2}
  END{printf "命中率 %.1f%%\n", 100*h/(h+m)}'
```

## 3. 汇总并写回论文（约 1 min）

```bash
python3 汇总压测结果.py out/50.jtl out/100.jtl out/200.jtl out/500.jtl \
        --hit 96.8,95.6,94.2,92.5 \
        --docx 科研积分系统论文-计算机系统应用版.docx
```

脚本会：

1. **丢掉每档最初 60 s 的爬坡样本**，只统计稳态段（`--warmup` 可调）；
2. 按 JMeter Summary Report 的口径算平均响应、95% 响应、吞吐量、错误率；
3. **用 Little 定律自检**——`吞吐量 × 平均响应 ÷ 并发数` 必须 ≤ 1，
   超了会报警（现在论文里 200/500 两档就是超了的，所以才要重跑）；
4. 把四行数据写进表 3，另存为 `…-实测.docx`。

输出长这样：

```
并发     平均/ms    95%/ms     吞吐/(次·s⁻¹)  错误率/%   命中率/%   利用率
50       86         142        486           0         96.8      0.836
         样本 145800 个，稳态 300 s
...
✅ Little 定律自检通过（吞吐 × 响应 ≤ 并发数）
```

## 跑之前先看这张"预期基线"

你说想要个模拟的照着做——**模拟值可以当校验尺，但不能当实测数据填进论文**。
下面这张表是按闭环排队模型推的**预期区间**，用途是：跑完真实压测后对一眼，
如果差得离谱，说明测试环境有问题（压测机和服务同机、连接池太小、爬坡段没切干净等），
而不是系统真这么慢。

无思考时间的闭环负载下，Little 定律是**恒等式**不是估计：

```
吞吐量 X = 并发数 N ÷ 平均响应 R        (无 timer 时精确成立)
实测 X 通常落在 N/R 的 84%~97%          (差额是 JMeter 自身调度与连接开销)
```

以你现有的响应时间为基准，四档应当落在：

| 并发 | 平均响应（你的实测） | X 的物理上限 N/R | **X 的合理区间** | 95%/平均 | 错误率 |
|---|---|---|---|---|---|
| 50 | 86 ms | 581 | **490 – 570** | 1.5~1.8× | ≈ 0 |
| 100 | 128 ms | 781 | **660 – 765** | 1.5~1.8× | < 0.2% |
| 200 | 216 ms | 926 | **780 – 905** | 1.6~1.9× | < 0.5% |
| 500 | 452 ms | 1106 | **930 – 1080** | 1.7~2.0× | < 1.5% |

**几条硬约束，真实数据一定满足，不满足就是测错了：**

1. `X × R ÷ N ≤ 1`——超过 1 物理上不可能（论文原来的 1053 和 1286 就是超了）；
2. X 随并发**先升后平**，不会一路线性猛涨；
3. R 在饱和点之后**超线性增长**（你的 216→452 就是典型的饱和后形态）；
4. 95% 响应约为平均的 1.5~2 倍，偏离太远说明有长尾抖动；
5. 缓存命中率随并发**缓慢下降**（热点集中度被稀释），不会上升。

汇总脚本会自动跑第 1 条自检。

## 如果实在跑不了

那就**别把表 3 当实测报**。两条退路，都比编数据强：

1. **降级为单档**：只报一个你确实测过的并发档位，表 3 缩成一行，
   正文说明"受测试环境限制仅完成 ×× 并发下的压力测试"。审稿人不会因为
   实验少而拒稿，但会因为数据不自洽而拒。
2. **整节删掉**：把表 3 和 3.6 节的命中率句子去掉，性能部分只留定性描述。
   论文的核心贡献是积分分配模型和标签权重模型，不靠这张表撑。

**现在表 3 里的 880 和 1050 是我上一轮按 `吞吐量 ≤ 并发数 ÷ 响应时间` 反推的，
不是实测值。** 投出去之前必须换成真值，或按上面两条退路之一处理。
